# tf-github-oidc-iac-role

This module creates one IAM role that GitHub Actions assumes with a short-lived OIDC token when it plans or applies the Delphi landscape. It does not create the GitHub OIDC provider. That provider already exists in the `github_oidc_provider` unit, and this role trusts its ARN, so a second provider is not registered in the account.

The `mode` input selects the permission set. A plan role can read the services this landscape manages and can write only the `.tflock` objects in the remote state bucket, which is what Terraform needs to take the lock during `plan`. It cannot write state objects and it cannot delete a bucket. An apply role can create and update the services the landscape modules use, including the ability to assume the DNS manager role that writes records in the hosted zone. Explicit denies stop that role from creating IAM users, calling AWS Organizations, deleting the state bucket, or deleting and rewriting the plan and apply roles themselves. Because of that last deny, a change to these two roles is applied from a break-glass profile on a laptop. The pipeline cannot widen its own trust policy.

The trust policy requires `token.actions.githubusercontent.com:aud` to be `sts.amazonaws.com` and `token.actions.githubusercontent.com:sub` to be the exact environment subject you pass in. When `job_workflow_ref` is set, the token must also name that workflow file on `refs/heads/main`. Leave `job_workflow_ref` empty for the plan role. A pull request runs the plan workflow from the merge commit, so a pin to `main` would reject every plan. Set it on the apply role so a pull request that edits the workflow still cannot assume the role that writes to AWS.

`oidc_subject` is the full `sub` claim, including the `repo:` prefix. The app-deploy role in `github_oidc_role` uses a different module that adds `repo:` for you, and copying those strings here without the prefix will never match. Repositories created after 15 July 2026, and repositories that have opted into immutable subject claims, put the owner id and repository id in the claim. Confirm the live claim before the first apply, because a name-form subject on a repository that issues the id form will not assume.

Adding a new AWS service to a module in this repository means extending the plan and apply statements in this module. The apply statement is a list of services rather than `AdministratorAccess`, so a service that is not listed fails closed.
